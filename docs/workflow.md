# ワークフロー

入口：[AGENTS.md](../AGENTS.md)

仕様書を作る手順と、各段で使うテンプレート・出すものの対応をまとめる。規則そのもの（要件の書き方、版と ID、承認前のチェックの観点、仮定の扱い）の正はプロジェクト「仕様書工房」の指示で、ここには写さない。この文書が持つのは「どの段で、どのテンプレートを使い、何を出すか」だけである。

## 全体の流れ

```mermaid
flowchart LR
  S1[1 受ける] --> S2[2 調べる] --> S3[3 聞き取る] --> S4[4 骨子] --> S5[5 たたき台] --> S6[6 確かめる] --> S7[7 承認]
  S7 --> S8[8 改訂]
  S8 --> S6
  S6 -->|指摘の対応| S5
```

## 段ごとの対応

各段の終わりに、スレッドで短く報告する。仕様書の 0（状態・版・次にやること）は段が進むたびに更新する。

| 段 | やること | 使うもの | 出すもの | 仕様書の状態・版 |
|---|---|---|---|---|
| 1 受ける | 対象・読み手・使い道・期限を確かめ、足りない項目だけを聞く。仕様書の種類を選ぶ | [質問票](../templates/hearing.md)、[テンプレートの選び方](../templates/README.md) | 埋めた「受けるときに確かめる項目」 | — |
| 2 調べる | 渡された資料と読めるリポジトリを読む。既存の仕組みに関わる要件は実物で確かめる | — | 確かめた事実と出典（仕様書の 4 と「根拠・出典」の列に入る） | — |
| 3 聞き取る | 分からないことを一度にまとめて質問する | [質問票](../templates/hearing.md) | 質問の一覧（おすすめの答え・理由・影響する要件つき） | — |
| 4 骨子 | 見出しと要件の一覧（ID と一行の説明）だけを出し、スコープと粒度の合意を取る | [本体のテンプレート](../templates/README.md) | 骨子 | 骨子・0.1 |
| 5 たたき台 | 骨子を埋める。【未決】【仮定】を 12 に載せる | 本体のテンプレート、[足す節](../templates/README.md)、[要件の文型](../templates/requirement-patterns.md) | たたき台 | たたき台・0.2〜 |
| 6 確かめる | 自分でチェックし、レビュワーに渡し、指摘ごとの対応を記録する | [検証スクリプト](../tools/README.md)、[レビュワーへの依頼文](../templates/review-request.md) | 指摘と対応の記録（仕様書の 13） | レビュー済み |
| 7 承認 | 【仮定】をユーザーに確かめ、承認を得る。版を上げ、13 に記録する | — | 承認済みの版。リポジトリに置く場合は PR | 承認済み・1.0 |
| 8 改訂 | 要件の追加・削除・優先度の変更は、ユーザーの承認を得てから行う。変更の理由・影響する要件 ID・日付を変更履歴に書き、6 と 7 をやり直す | 元の仕様書 | 新しい版 | 1.1（要件の追加・削除を含むなら 2.0） |

## 置き場所

- 作成中の版は Claude Docs に置く。使えなければプロジェクトのファイルに Markdown で置く。
- このリポジトリ（specFILE）には仕様書を置かない。置くのはテンプレートと手順だけである（仕様書を作らない作業で、関係のない仕様書を読まずに済むため）。
- ユーザーが実装用のリポジトリを置き場所に指定したとき、または AI に実装させるためにそこへ置くときは、承認済みの版を Markdown にして、そのリポジトリへの PR にする。
- 文書を分けたら、入口の文書の文書一覧に行を足す。

## 6（確かめる）の順番

1. リポジトリに Markdown がある場合は `python3 tools/check_spec.py <ファイル>` を実行し、エラーを 0 件にする。Claude Docs だけにある場合は、Markdown に書き出して同じように確かめる。
2. プロジェクトの指示の「承認前のチェック」の観点を自分で通す。スクリプトが見るのは形だけで、矛盾や抜けは見ない。
3. [レビュワーへの依頼文](../templates/review-request.md) と仕様書だけをレビュワーに渡す。
4. 指摘を 1 件ずつ仕様書の 13 に記録し、対応するか、見送る理由を書く。

## スレッドでの報告に入れるもの

- 仕様書へのリンク、状態、版。
- 残っている【未決】【仮定】の数と、主なもの。
- 親の仕様書を変えた場合は、影響する子の仕様書と要件 ID。
- 最後の報告には、指示に書かれていないことで迷った点、指示どおりでは困った点を一行で書く。

## 工房の整備

テンプレート、このワークフロー、プロジェクトの指示を直す手順。整備用のスレッド「仕様書工房の整備」で行う。

| 直すもの | 契機 | 手順 |
|---|---|---|
| テンプレート、ワークフロー、検証スクリプト | 仕様書を作っていて形が合わなかった。指示が変わった | 整備用のスレッドで直し、`python3 tools/check_spec.py` を通して PR にする。ユーザーがマージする |
| プロジェクトの指示 | 各スレッドの最後の報告にある「迷った点」のうち、複数の仕様書で同じ直しが要るもの | コーディネーターが集め、整備用のスレッドで差分（直す前と直した後）にしてユーザーに提案する。ユーザーがプロジェクト設定を直す。そのあと、このリポジトリの文書を指示に合わせる |

指示とこのリポジトリの文書が食い違ったら、指示に従い、リポジトリの側を直す。
